# Bareline — Technical Architecture & Code Quality Review

Reviewed at commit `51cd4c0` (working tree dirty). Every file:line below was read directly; counts come from `rg`/`cargo check`/`cargo fmt --check` runs on this tree. The command inventory was produced by actually running `target/debug/bareline.exe --no-extensions --export-command-inventory ... --inventory-commit 51cd4c0...` (444 command IDs).

## 1. Architecture summary

The workspace is a layered Rust monorepo (edition 2024, `windows = 0.62`, `winit = 0.30`). Neutral core crates form a clean DAG: `document` (piece-tree snapshots, paged sources) ← `file-io` (codecs, lifecycle, recovery, session) ← `editor-surface` (resident `EditorSurface` + `PagedEditorSurface`, power editing, completion, layout) ← `app` (`Workspace`, `WorkspaceEditor` enum, find/search-panel/settings/macros/compare/views controllers) ← `apps/bareline` (the `Shell` composition root). Cross-cutting crates: `commands` (registry, `Keymap`, discovery), `settings`, `search` (PCRE2 FFI), `syntax` (Lexilla bridge; depends on `search` for outline regexes), `diff`, `macros`, `ui` (immediate-mode widgets emitting `renderer::DrawOp`), `renderer` (backend-neutral `DrawOp`/`TextBackend`), `extensions-protocol`/`extension-sdk` with a separate `apps/extension-host` process over authenticated pipes, and `apps/update-helper`. All `windows::`/`windows-core` usage is confined to `crates/platform-windows` (Win32 window/menu/UIA/clipboard/watch + the Direct2D/DirectWrite renderer in `platform-windows/src/renderer.rs`; there is no separate `renderer-d2d` crate). The **Windows-type boundary rule is respected** — the only Win32 leak outside is a raw `extern "system"` QPC declaration in `apps/bareline/src/windows_app/performance.rs:62` and `std::os::windows` helpers in `crates/platform`. **Threading model:** one winit event-loop thread (`EventLoop<usize>`; `user_event` is a generic "wake"); all I/O runs on ad-hoc `std::thread::spawn` threads (64 spawn sites) or a few global single-thread workers (`paged-view-io` in `editor-surface/src/paged_view.rs:50`, `columns.rs:7`, `file-io/src/resident_recovery.rs:24`, one `SearchWorker`), with results returned through `mpsc::sync_channel(1)` and drained by ~25 `*_pump()` methods invoked on every wake (`windows_app.rs:345-410`). **Rendering** is immediate mode: each `RedrawRequested` (`windows_app.rs:2411`) rebuilds a `Vec<DrawOp>` from `bareline_ui::shell_with_theme` + `views.draw` + overlays and hands it to the D2D renderer; per-line text layouts are cached in `EditorSurface::layouts`. No async runtime is used, per AGENTS.md.

### Command inventory cross-check

444 registered IDs (exported from the binary). Every ID has a reachable handler except as noted: the `ext.*` family (8 ids) is always enabled but always fails (ARCH-01); `view.fold.all` aliases level-1 folding (ARCH-20); for paged active documents `search.find/replace/find_next/find_previous/replace_one/replace_all`, `view.split_*`, `view.clone_other`, `view.move_other` and (if any tab is paged) `search.open_documents` are disabled by static gates (ARCH-02). No registered ID reaches the `execute_power` catch-all under normal routing, but the routing is implicit (14-deep boolean chain) rather than table-driven, so this is not enforced (ARCH-06).

### Things that are in good shape

- Windows type containment: `windows::`/`windows-sys` appear only in `crates/platform-windows` (verified by grep); the neutral `app`/`editor-surface`/`document`/`file-io` crates have zero `unsafe`.
- Blocking I/O discipline: every `std::fs` call reachable from the event loop that I traced (`macros.rs:480`, `settings.rs:228`, `recovery.rs:385`, `workspace_panels.rs:460`, `launch.rs:91`, `inventory.rs:187`, `language.rs:334`) is inside a spawned thread; the 1 ms `thread::sleep` loops in `launch.rs:136,146`, `paged_navigation.rs:175`, `utilities.rs:44` are all on workers.
- Compiler warnings: only the three dead-code warnings above across the whole workspace.
- Command registry + inventory validation (`inventory.rs:150-171`) enforces unique, well-formed IDs at startup.
