# Technical audit — current local working tree, 12 September 2026

This is a fresh audit of `Bareline-Editor`, not the three older closure worktrees. Baseline HEAD is `51cd4c0` **plus the existing uncommitted changes**. The executable was rebuilt locally. No remote was inspected or contacted. Production source was not edited. `../evidence/source-manifest.json` pins the application, core, extension, build and packaging files; `working-tree-status.txt` records pre-existing changes.

Evidence labels: **reproduced** means the current code was executed against generated fixtures; **native** means observed in the running Windows app; **source** means a complete relevant code path was inspected; **qualification gap** means required evidence or delivery is absent, not that a particular runtime defect has been proven. Severity: P1 = data safety/core workflow or release blocker; P2 = meaningful reliability/usability risk; P3 = maintenance/contract debt. No P0 exploit or universal crash is claimed.

## Reproduction detail and consequences

**TECH-001.** The exact `sweep_temp_caches` implementation was extracted unchanged into `evidence/launch_probe.rs`. Under the audit fixture, `temp/Bareline-junction` pointed to another generated directory outside `temp`. It contained `cache-4294967294-1/keep.txt`. The helper followed `is_dir`/`read_dir`, accepted the embedded PID as dead and removed that child. Output: `junction_sentinel_before=true`, `sweep_removed=1`, `junction_sentinel_after=false`. Only generated files inside the verified audit fixture were affected. This establishes missing containment, not a cross-user privilege escalation. `process_alive` also maps query failure to dead; the plan requires an Unknown state.

**TECH-002.** A generated roaming settings file was held with a no-sharing Windows handle. Migration created the local directory but the rename failed. After releasing the handle, invoking migration again still did nothing because `local.exists()` causes early return. Both outputs show settings remain only in roaming. Redirected profiles/cross-volume rename failure are additional source-supported triggers, not separately exercised.

**TECH-003.** The save layer correctly treats `expected=None` as create-new-only. The bug is that the UI supplies no captured destination identity for an explicitly approved overwrite. Sol reproduced selecting an existing scratch file, approving the native dialog, receiving a misleading “File changed” conflict, keeping a dirty Untitled tab, and leaving `.bareline-…tmp` containing the replacement. Save Copy and paged Save As share the same missing contract; their scope is source-confirmed unless the native report says otherwise.

**TECH-004.** `save_probe.rs` injects an external writer at `LocalFileSystem::commit`, exactly after the production fingerprint checks and before the actual `WindowsFileSystem.commit`. That adapter writes a different payload, then invokes the real `ReplaceFileW` implementation. The save succeeds and only the editor payload remains. This is a deterministic reproduction of the race window, not a claim that random simultaneous editing was observed. A second pre-commit fingerprint would merely narrow the race; preservation of the displaced file must be part of the fix.

**TECH-005/006.** The newest discard fix retries deletion but still returns `()`, discards `retire_paths`, clears both generations and resets public status even if no deletion succeeded. The same method contains `recv_timeout` and `sleep`, and is called synchronously through `EditorSurface::discard_recovery`. No disk-lock native reproduction was forced in this pass; the bounded wait and silent-failure paths are explicit in the source. Keep this distinct from the already-fixed successful-discard generation leak.

**TECH-007/008/009.** `task_probe.rs` includes the current `task.rs` directly. It waits until notify before canceling, then observes `Some(42)` after cancel. Dropping a running task yields `drop_signalled_cancel=false`. A controlled worker panic leaves `poll=None`, reported workers/running both 1, and the next submission rejected. A two-worker experiment leaves a third job blocked behind worker 0 after worker 1 has become idle; releasing worker 0 immediately unblocks it. Current production consumers are launch navigation and paged accessible text; this is not a claim that all features already use this pool.

**TECH-020.** A fresh subprocess of the current binary received `--version` and isolated APPDATA/LOCALAPPDATA/TEMP/TMP. It printed `Bareline 0.1.0`, exit 0, while the generated roaming settings file moved into local storage and the cache sentinel was deleted. The source performs migration at line 350 and sweeping at line 404 inside parsing, before the caller checks `version`/`help`. It computes the installed migration even before selecting the portable/performance root. Thus a command that should only report metadata performs unrelated persistent work and pays filesystem cost before first frame.

**TECH-021/022.** Current `LaunchRuntime::queue` (`launch.rs:41–54`) accumulates at most 256 pending paths. `launch_pump` (`:63–72`) blindly retains a missing editor, without checking a terminal open failure or `Workspace::path_loading`; other consumers such as instance/search/session explicitly use that distinction. Failed paths therefore never free admission slots. `instance.rs:75–79` refuses a subsequent handoff if `queue` is full. Separately, the only `navigation = None` assignment is after successfully locating the associated editor and polling a result (`launch.rs:65–89`). A tab closed while that non-editor-busy task runs can strand its slot. These are source-confirmed lifecycle defects; no 256-request native saturation run or close-during-navigation timing reproduction was performed.

## Limits

This is a broad local code and runtime audit, not proof that every defect has been found. Native macOS/Linux operation, physical IME/AltGr/dead keys, Narrator, mixed-monitor DPI, both Windows support-floor versions, signed owner distribution and clean-VM install/update were not all executed. Cached advisory checks are dated evidence and are not a fresh online vulnerability attestation. See the test report and native coverage for exact outcomes.
