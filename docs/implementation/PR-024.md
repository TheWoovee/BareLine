# PR-024 implementation and evidence

Status: IN_PROGRESS. Authority: ADR-06, FC-09, FR-030 and PR-024.

Implemented source:

- Neutral validated semantic snapshots in platform; PR-023 semantic conversion and bounded editor projection in app. IDs, hierarchy, role/name/value/state, focus and action capabilities are retained.
- Actual AccessKit Windows UI Automation provider, using native HWND subclassing for WM_GETOBJECT and window focus. Tree activation is lazy; changes are diffed and AccessKit events raised outside shared-state locks. Cross-thread actions enter a bounded 256-item queue and wake the UI thread. Requests for disabled/unknown targets and invalid text positions are rejected.
- Editor TextPattern contains the layout-established visible range only, with a hard 64 KiB ceiling. Grapheme lengths and absolute byte selection conversions preserve emoji/combining sequences and CRLF. Offscreen selections are omitted instead of clipped into a false selection; graphemes exceeding AccessKit's u8 length cannot be faithfully represented, so that range is omitted.
- Accessible previous/next viewport Invoke controls request one screen through the host. IME preedit is a bounded live Status node; it is not an active composition text range.
- Host initializes before window visibility, updates after layout, routes editor/palette actions and selection, and owns adapter lifetime.

Dependency rationale: accesskit =0.25.0 and accesskit_windows =0.35.0 are ADR-09 approved and compatible with Windows 0.62/Rust 1.85. Native subclassing handles the winit-owned HWND directly, so accesskit_winit is unnecessary. AccessKit requires initialization before showing a window to prevent nested WM_GETOBJECT initialization races; the expensive semantic tree still activates only when requested. This follows the upstream provider requirement rather than constructing a provider inside WM_GETOBJECT.

Focused evidence (2026-09-06, Windows locked desktop; no GUI launched):

- `cargo check -p bareline-platform-windows --lib`: PASS.
- `cargo test -p bareline-platform-windows accessibility --lib`: PASS, 4 tests. Hard-line/trailing-line identity, actual AccessKit tree values/selection, provider action conversion at a 5,000,000,000-byte base, invalid HWND and malformed model rejection. The large offset test is not a 5 GiB document integration test.
- `cargo test -p bareline-app accessibility --lib`: PASS, 1 test. Grapheme/CRLF offsets, offscreen selection omission, oversized text rejection. An unrelated app registration unused-Result warning was present.
- Touched files formatted with rustfmt edition 2024. Platform clippy reached the provider without local warnings; final attempt blocked by watch.rs:132 needless borrow outside this PR. Accessibility local lint corrected and provider tests rerun.

Ordinary implementation gaps (not lock blockers): transparent TextRange paging beyond the exposed viewport; native active composition ranges; complete default/all-panels semantic goldens and per-surface runtime composition/focus/action coverage. AccessKit Windows 0.35 exposes TextPattern and ScrollItemPattern but not ScrollPattern or composition APIs. Its TextRange providers are private implementation types, so a custom range layer cannot be attached through the public Adapter API. Implementing transparent paging requires an upstream AccessKit provider extension or replacing the editor's provider via a native fragment subtree, with range identity, lifetime, asynchronous source availability and UIA query tests. Explicit viewport navigation does not claim to fulfill transparent range movement. Keep PR-024 IN_PROGRESS until these ordinary gaps are resolved.
